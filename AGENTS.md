# Инструкции для агентов

## Контекст репозитория

Это коллекция учебных работ ИТМО по направлению «Информатика и вычислительная техника».
Работы независимы: общей сборки, единого окружения и общего набора тестов нет.

- Структура: `SemesterN/<дисциплина>/<работа>/`. Встречаются `LabworkN`, `AssignmentN`, `ResearchN`, `MasterClassN`, семинары и домашние задания.
- `Semester1` и `Semester2`: Java, Python, ассемблер, SQL, отчёты и материалы базовых дисциплин.
- `Semester3`: C/ассемблер в `ProgrammingLanguages`, Java и веб-приложения в `WebProgramming`.
- `Semester4`: алгоритмы (`AaDS`), архитектура компьютера (`CSA`), программная инженерия (`SEB`), математика и физика.
- `Semester5`: `AISystems`, `CircuitDesign`, `Electronics`, `EmbeddedSystems`, `Modeling`, `OS-new`.
- Корневой `README.md` содержит оглавление, но может отставать от фактической структуры. Уточняй содержимое по файлам выбранной работы.

## Перед изменениями

1. Проверь `git status --short` и сохрани существующие изменения пользователя, включая неотслеживаемые файлы.
2. Определи семестр, дисциплину и конкретную работу. Прочитай её `README.md`, локальный `AGENTS.md`, условие и требования в `docs/`, `task.pdf`, `variant.md` или аналогичных файлах, если они есть. Более близкий к файлу `AGENTS.md` уточняет эти правила.
3. Уточни вариант задания, интерфейсы, формат ввода-вывода и требования к отчёту. Используй данные конкретной работы; номер варианта и параметры из соседней лабораторной могут отличаться.
4. Выбери инструменты по локальным манифестам, скриптам и конфигурации. Версии Java, Python и других инструментов различаются между работами.

## Область изменений

- Вноси минимальные изменения в выбранную работу и непосредственно связанные с ней тесты, данные и документацию.
- Сохраняй структуру каталогов, стиль окружающего кода, имена пакетов, точек входа и файлов, ожидаемых проверяющей системой.
- Соблюдай ограничения задания: требуемый язык, алгоритм, библиотеки, архитектуру и формат результата. Учебную реализацию алгоритма нельзя заменять библиотечным вызовом, если требуется реализовать его самостоятельно.
- Повторно используй существующие зависимости. Обновляй версии, систему сборки и форматирование только в рамках задачи.
- Не редактируй сторонние библиотеки, SDK и сгенерированные файлы без необходимости. В STM32-проектах учитывай границы `USER CODE` и настройки генератора.
- Не добавляй окружения, кэши, временные файлы и результаты сборки. Уже хранящиеся в репозитории PDF, изображения, архивы и данные могут быть частью сдачи; сохраняй их назначение.
- Документацию и ответы пиши по-русски, если задача или локальные правила не требуют другого языка. Сохраняй принятый язык идентификаторов в коде.

## Git-сабмодули

Многие работы подключены как отдельные репозитории. Среди них: `Semester3/ProgrammingLanguages/Assignment1`–`Assignment4`, часть `Semester3/WebProgramming`, `Semester4/AaDS`, `Semester4/CSA/Labwork4`, часть `Semester4/SEB`, `Semester5/OS-new` и шаблоны в `Semester5/CircuitDesign`.

- Сверяй `.gitmodules` с фактическими gitlink-записями: `git ls-files --stage` (режим `160000`).
- Перед редактированием проверь статус внутри нужного сабмодуля через `git -C <путь> status --short`; корневой diff не раскрывает его изменения.
- Если нужный сабмодуль не инициализирован, загружай только его: `git submodule update --init -- <путь>`.
- Сохраняй закреплённые версии остальных сабмодулей. Избегай массового `update --remote` и изменений `.gitmodules`, не связанных с задачей.
- Проверяй diff внутри изменённого сабмодуля и в корне. Обновление gitlink должно соответствовать нужному коммиту вложенного репозитория.

## Проверки

Запускай проверки из каталога соответствующего проекта. Ниже — примеры из существующей конфигурации; перед запуском сверяй их с текущими файлами работы.

| Каталог | Проверка |
| --- | --- |
| `Semester1/ComputerScience/Labwork3` | `python -m pytest` с зависимостями из локального `requirements.txt` |
| `Semester2/Programming/Labwork5` | `./mvnw test` |
| `Semester2/Programming/Labwork7` | `./gradlew check` |
| `Semester3/WebProgramming/Labwork4-front` | `npm run lint` и `npm run build`; зависимости зафиксированы в `package-lock.json` |
| `Semester4/CSA/Labwork4/python` | `poetry run pytest . -v` |
| `Semester4/Physics/Labwork1` | `cargo test` |
| `Semester4/Physics/Labwork4` | `go test ./...`; учитывай системные зависимости raylib |
| `Semester5/CircuitDesign/Labwork1` | `make test-register`, полная проверка — `make test`, сборка отчёта — `make report` |

- Для других Maven/Gradle-проектов предпочитай локальные `mvnw`/`gradlew`, если они есть. Для C/C++ и HDL изучи цели локального `Makefile` или конфигурацию CMake.
- Python-зависимости устанавливай в окружение конкретной работы. Для расчётных скриптов и ноутбуков проверь воспроизводимый запуск и содержательные результаты на данных задания.
- При изменении логики используй существующие тесты; добавляй небольшую проверку нового поведения или исправленной ошибки, когда это необходимо. Для правок документации достаточно проверить текст, пути и команды по исходным конфигурациям.
- Некоторые работы являются заготовками с намеренно падающими тестами. Разбирай причину ошибки и не отключай проверки ради успешного статуса.
- В результате укажи выполненные проверки и их исход. Если запуск требует недоступного ПО, оборудования или окружения, явно назови непроверенную часть.

## Расчёты и отчёты

- Сначала изучи условие, вариант и исходные данные; сохраняй единицы измерения, формулы, точность и требования к оформлению.
- Редактируй исходники (`.typ`, `.tex`, `.md`, `.ipynb` или скрипт генерации) и пересобирай связанные артефакты, когда меняется их содержание. Команды бери из локального `README.md` или `Makefile`.
- Проверяй согласованность кода, таблиц, графиков, выводов и итогового отчёта. После пересборки PDF просматривай страницы на обрезанный текст, неверные переносы и пропавшие изображения.
- Сохраняй исходные измерения и входные файлы. Указывай способ получения результатов и параметры моделирования, необходимые для повторного запуска.
- Различай расчёт, программную симуляцию, запуск в целевой среде и эксперимент на оборудовании. Не представляй симуляцию как измерение на плате, а Python-модель как проверенный запуск GPSS World.
